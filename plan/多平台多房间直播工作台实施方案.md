# 多平台多房间直播工作台实施方案

> 状态：实施中（房间识别、关注联动及多房间核心已进入实现；回溯、发送与凭据安全仍待后续阶段）
> 适用项目：DTV（Wails v3 + Go + React）  
> 目标：在保留现有单房间播放体验的前提下，增加多平台、多房间监看工作台。

## 1. 需求范围

### 1.1 产品目标

- 在独立的“添加直播间”页粘贴链接并识别平台与房间；识别成功、取得房间资料后自动加入关注列表。
- 同一工作台最多监看 16 个不同房间。
- 在独立的“多房间工作台”页拖入已关注主播即可加入并播放。
- 支持 1×1 至 4×4 网格；默认 2×2；支持拖入房间、移动卡片和调整卡片尺寸。
- 每个房间独立音量；支持单路音频焦点，以及 Shift 多选后多路播放声音；支持音量增强。
- 支持全局及单房间弹幕开关。
- 斗鱼登录后可发送普通文本弹幕。
- 每个房间保留最近约 120 秒回溯，可预览并导出 GIF / MP4。
- 房间、布局、音频和弹幕偏好保存在本机。
- Windows 上的斗鱼会话以当前 Windows 用户为保护范围加密保存。

### 1.2 本轮明确不做

- 不替换或删除现有 `/player` 单房间播放器；新功能先以独立工作台入口交付。
- 不增加云端账号、云同步或默认 LAN 同步。
- 不实现礼物、关注、点赞等弹幕以外的平台互动。
- 不承诺 16 路在所有硬件上都能达到实时帧率；16 路是产品上限，不是最低硬件保证。
- 不在前端 localStorage、配置导出或同步 payload 中保存明文斗鱼 Cookie。

## 2. 当前项目基础与需要调整的地方

- Wails IPC 服务在 `internal/services`，平台客户端在 `internal/platforms`，应用装配入口是 `main.go`。
- 前端平台统一入口是 `frontend/src/api/index.ts`，现有单房间页面为 `frontend/src/screens/PlayerPage.tsx`，播放器封装为 `frontend/src/features/player/useXgPlayer.ts`。
- 前端偏好目前主要经 `frontend/src/lib/storage.ts` 写入 localStorage。
- 当前播放器采用每个页面一个 xgplayer 实例；播放器音量限制在 0–1，音量设置是全局值。
- 斗鱼弹幕管理器当前以单房间连接为模型；多房间监看需要调整各平台弹幕生命周期与并发管理。
- 斗鱼扫码登录目前通过 Service 返回登录结果，现有前端状态会使用 Cookie；DPAPI 迁移必须同时改变凭据流转方式，不能只在磁盘上加密。
- 直播流、弹幕协议及平台 URL 格式受第三方接口影响，应把平台差异封装在平台适配层，不写进网格组件。

## 3. 总体架构

### 3.1 页面与组件

新增两个独立路由：`/add-room` 负责链接识别及自动关注，`/monitor` 负责多房间播放工作台；现有 `/player` 保持不变。顶栏页签顺序为“添加直播间 → 多房间工作台 → 订阅分区 → 平台”。
“多房间工作台”页签仅显示图标，并提供可访问名称。

建议前端结构：

```text
frontend/src/features/multiview/
  MonitorPage.tsx
  MonitorToolbar.tsx
  RoomGrid.tsx
  RoomTile.tsx
  AddRoomDialog.tsx
  useMonitorWorkspace.ts
  layout.ts
  roomUrl.ts
  audioFocus.ts
  replay/
```

职责边界：

- `roomUrl.ts`：只做 URL 规范化与平台识别，不访问任意 URL；识别页通过平台 API 获取房间资料后调用关注状态管理。
- `layout.ts`：布局校验、碰撞处理、网格尺寸与持久化 schema 迁移。
- `useMonitorWorkspace.ts`：房间列表、布局、音频选择及全局/单房间开关。
- `RoomTile`：单房间信息、播放器、弹幕层、音量和错误态。
- 平台 API 仍由现有 `frontend/src/api` 分流；播放器使用现有 xgplayer 配置和弱网重试策略。

### 3.2 Go 服务与平台适配

- 复用现有平台 `GetStreamInfo`、`StartDanmaku`、`StopDanmaku` 等能力。
- 将各平台弹幕管理器改为按房间管理 session：`Start(roomID)` 幂等或返回明确状态，`Stop(roomID)` 只停止目标房间，`StopAll()` 在应用退出时停止所有 session。
- 为多房间弹幕设置全局上限和连接失败退避；避免每次开关造成重复连接。
- 斗鱼发送能力封装在 `internal/platforms/douyu`，由 `DouyuService` 做参数校验与 IPC 暴露。
- `main.go` 只负责注册新服务或注入依赖，不承载平台协议、URL 解析或布局逻辑。

### 3.3 本地状态

建议单独使用版本化工作台数据，不与关注列表或订阅分区混用：

```ts
interface MonitorWorkspaceV1 {
  version: 1;
  grid: { columns: 1 | 2 | 3 | 4; rows: 1 | 2 | 3 | 4 };
  rooms: MonitorRoom[];
  globalDanmakuEnabled: boolean;
  selectedAudioRoomKeys: string[];
}

interface MonitorRoom {
  key: string; // `${platform}:${canonicalRoomId}`
  platform: LivePlatform;
  roomId: string;
  title?: string;
  nickname?: string;
  layout: { column: number; row: number; columnSpan: number; rowSpan: number };
  volume: number; // 0..1；增强增益另行存储或设置上限
  gain: number;
  danmakuEnabled: boolean;
  replayEnabled: boolean;
}
```

持久化规则：

- 只保存标准房间 ID、用户偏好和布局，不保存播放 URL、临时 token、Cookie 或弹幕内容。
- 校验并修复非法布局、重复房间及超出 16 路的数据；迁移失败时显示可恢复错误，不覆盖原始数据。
- 使用版本化 localStorage key；必要时迁移到 IndexedDB，尤其是回放数据不能放 localStorage。
- 工作台状态默认不进入现有 JSON 配置导出或 LAN 同步，除非产品另行明确要求。

## 4. 关键功能设计

### 4.1 链接识别与加房

1. `/add-room` 输入完整 URL 或可明确归属某平台的规范房间地址。
2. 解析并校验协议、主机名、路径和房间 ID，映射到 `platform + canonicalRoomId`；获取房间资料成功后自动加入已关注列表，已关注时保持原记录不重复切换。
3. `/monitor` 通过拖入关注列表中的主播加入工作台并开始播放；重复房间不重复添加，超过 16 路时拒绝并提示当前数量。
4. 对无法解析的链接返回具体原因，不静默回落到某个平台。
5. 抖音短链接若必须解析跳转，应由专用后端逻辑处理：
   - 只接受 HTTPS；
   - 每次请求和每次重定向都校验平台域名 allowlist；
   - 禁止 localhost、私网 IP、非 HTTP(S) scheme 和跨到非平台域名；
   - 设置超时、最大重定向次数和响应体上限。
6. 第一版只支持确认过的常见房间 URL；平台格式清单和样例 URL 纳入测试。短链解析作为单独能力验证，不能影响普通 URL 添加。

### 4.2 网格与拖拽布局

- 网格列数、行数分别限制为 1–4。
- 默认网格 2×2；工作台从关注列表拖入主播，也可接受来自其他来源的有效房间链接拖放。
- 每个房间占用一个或多个逻辑网格单元，布局坐标使用整数；`columnSpan`、`rowSpan` 不得越过网格边界。
- 拖动或缩放提交前校验重叠；优先尝试最近的可用空位。若不存在可用位置，回滚并提示，不静默挤掉其他房间。
- 网格变化时按确定性规则重新排布；布局保存后重启恢复。
- 将一个房间拖到另一个房间上时，交换两者的网格位置和卡片尺寸；其他房间的位置保持不变。
- 卡片尺寸支持 Ctrl+滚轮快速缩放，以及拖拽右/下边缘或右下角按网格单元手动调整。
- 不显示卡片尺寸下拉按钮；Ctrl+滚轮和边缘拖拽仍可调整尺寸。

### 4.3 多路播放与资源管理

- 每个房间拥有独立播放器实例、加载/断流/重连状态和弹幕订阅。
- 房间移除、平台/房间 ID 更换、页面卸载时必须停止播放器、定时器和订阅。
- 可见网格中的房间默认播放；被移出工作台的房间不在后台持续取流。
- 保持现有 URL/清晰度/线路选择及断流重连行为；避免复用单房间页面中的全局状态导致串房。
- 对 16 路增加资源告警或低负载建议。性能优化可考虑非聚焦房间降清晰度或暂停，但不能未经用户同意改变清晰度/声音。

### 4.4 音频焦点、音量与增强

- 默认音频焦点为单路；选择另一房间时取消原焦点。
- 普通鼠标左键点击房间可直接将其设为音频焦点。
- Shift 多选只改变音频选择集合，不影响房间布局或弹幕选择。
- 每路保留 0–100% 音量；焦点之外的房间静音。房间音量为 0 与“非焦点静音”需分别建模，避免恢复焦点时覆盖用户音量。
- Shift+鼠标左键点击单个房间可切换该房间声音；普通音频焦点与 Shift 多选维持原有操作。
- 音量增强通过 Web Audio `GainNode` 实现，增益上限可配置但必须有安全默认值；增强音量可能削波，应提供削波提示或限制峰值。
- 对媒体元素设置跨域属性必须早于媒体加载；逐平台验证 HLS、FLV 和不同 CDN 的 CORS 行为。音频不能进入 Web Audio 时显示“该线路不支持增强”，退回普通音量，不允许静默输出无声。
- Web Audio 初始化应由用户手势触发，并在页面隐藏/关闭时释放节点和 `AudioContext` 资源。

### 4.5 弹幕

- 全局开关控制是否允许弹幕订阅；单房间开关是全局开启时的局部过滤。
- 全局关闭后应停止全部后台弹幕连接，而不只是隐藏弹幕 UI。
- 单房间关闭后停止该房间连接；重新开启只创建一个连接。
- 多路事件按 `roomId + platform` 路由到对应 tile；切换房间、重复事件和迟到事件不得串到其他房间。
- 弹幕 UI 可以每路显示或隐藏，消息事件仍采用批量渲染、有限队列，避免 16 路高频更新导致 React 整页重渲染。

### 4.6 斗鱼文本发送

- 仅斗鱼且登录有效时显示发送入口；其他平台不显示或明确标记为不支持。
- 第一版仅普通文本，不接受 HTML、富文本或本地命令。
- 后端检查房间号、登录状态、空文本、长度限制；前端进行同等校验并展示状态。
- 设置合理的发送节流，处理平台拒绝、登录过期、网络错误，并避免重复点击重复发送。
- 发送结果必须明确呈现；不得将本地“提交成功”冒充平台已确认发送。
- 需要验证斗鱼普通用户登录会话的发送协议、必要鉴权字段、房间加入流程及服务端回执；未确认协议前不进入产品实现。

### 4.7 120 秒回溯与导出

建议采用两阶段实现：

**回放缓存**

- 使用浏览器媒体捕获能力对单房间播放输出分段录制；按时间戳维护约 120 秒 ring buffer。
- 缓存启用状态按房间保存，明确展示“缓冲中 / 可回放 / 不支持”。
- 对每路设置缓存上限，并设置进程级总内存预算；达到预算后淘汰最早分段或暂停新增缓存，不允许无限增长。
- 只在用户开启回溯时录制；关闭后释放该房间缓存。
- 回放预览应覆盖视频和音频，确保不会因音频焦点机制把回放声音错误静音。

**导出**

- 浏览器 `MediaRecorder` 格式能力依赖 WebView2 版本和系统编码器；实现前做真实目标机 spike，记录支持的 MIME/codec。
- 导出不能把大型 Base64 文件直接塞入 Wails JSON IPC。使用有随机一次性 token 的本地回环导出服务或受控分块 IPC，将录制分段流式写入临时文件。
- MP4 和 GIF 若不能由 WebView 原生可靠生成，采用受控的本地转换器方案；在决定打包 FFmpeg 前评估体积、许可证、跨平台构建和更新方式。
- MP4 可包含音频；GIF 是无声格式，需在 UI 和导出结果中明确说明。
- 导出中途取消、磁盘空间不足、编码器不可用和文件写入失败都必须清理临时文件并明确报错。
- 回放数据默认仅存内存/临时文件，不上传、不自动进入配置同步；用户主动导出后才写入用户指定路径。

## 5. 斗鱼凭据本地保护

### 5.1 Windows 实现要求

- 使用 DPAPI `CryptProtectData` / `CryptUnprotectData` 的当前用户范围（不使用 LocalMachine 范围）。
- 密文文件放在当前用户 DTV 配置目录，权限限制为当前用户；明文只短暂存在于内存。
- DPAPI 解密失败时报告需要重新登录；禁止回退为明文文件或 localStorage。
- 凭据读写仅由 Go 后端完成，renderer 不再读取或写入 Cookie。
- QR 登录成功后由后端保存 Cookie，IPC 返回登录状态和必要的非敏感 profile，不返回 Cookie 字符串。
- 新增状态查询接口；退出登录时清除客户端 Cookie jar 与 DPAPI 凭据。

### 5.2 迁移与其他系统

- 首次启动若发现旧版 `douyu_cookie` localStorage，前端仅一次性提交给后端迁移；确认保存成功后删除旧键。失败则保留旧值并提示，不得误删。
- 迁移过程避免日志打印 Cookie、请求头或完整登录结果。
- macOS/Linux 需要单独采用系统钥匙串/Secret Service；若本轮不实现，必须明确说明不提供同等级的持久化凭据保护，不能静默明文降级。
- 检查 `configTransfer`、LAN sync、调试日志和错误信息，保证不会输出或打包 Cookie。

## 6. 分阶段实施

### 阶段 0：技术验证与接口确认

- 整理四个平台的标准房间链接及短链行为。
- 验证 WebView2 中 FLV/HLS 多路播放、`captureStream`、MediaRecorder MIME、音频 CORS/GainNode。
- 确认斗鱼弹幕发送协议与回执。
- 评估 4/9/16 路的 CPU、GPU、内存和网络基线。
- 明确 MP4/GIF 转码器的许可证和发行包影响。

**退出条件：**上述不可逆技术决策均有 Windows 实机结果；若能力不支持，形成明确降级方案后再开发。

### 阶段 1：工作台核心

- 路由、房间 URL 解析、最多 16 路房间模型。
- 1×1 至 4×4 网格、默认 2×2、拖放/缩放/持久化。
- 每房间播放器生命周期与错误隔离。
- 房间、布局和偏好本地保存。

### 阶段 2：音频与弹幕

- 多房间弹幕 session 管理和资源释放。
- 全局/单房间弹幕开关。
- 独立音量、单路焦点、Shift 多选。
- 经验证的平台启用音量增强，其余线路明确降级。

### 阶段 3：斗鱼发送与凭据安全

- DPAPI 后端存储与现有 Cookie 迁移。
- 修改二维码登录 IPC，不再向前端暴露 Cookie。
- 斗鱼普通文本发送及频率限制、结果反馈。

### 阶段 4：回溯与导出

- 每房间 120 秒分段缓存、总内存预算和回放预览。
- 流式本地导出。
- 根据阶段 0 验证结果交付 GIF/MP4；能力不足时不能以扩展名伪装格式。

### 阶段 5：打包与回归

- Windows/macOS/Linux 构建和安装包验证。
- 大量房间开启/关闭、重启恢复、网络中断、登录过期、磁盘不足、导出取消等回归。
- 更新 README、设置说明、隐私说明和已知限制。

## 7. 验收标准

### 功能

- 四个平台的测试链接能正确识别平台与规范房间 ID；非法 scheme、未知域名和格式错误链接被拒绝。
- “添加直播间”和“多房间工作台”是独立页签；识别成功后自动关注，已关注房间不会被重复加入。
- 从关注列表拖入主播后工作台新增对应卡片并开始取流播放，关注记录本身不被移动或删除。
- 可添加 16 个不同房间；第 17 个被拒绝并说明原因；重复房间不会重复播放。
- 网格支持 1×1、2×2、3×3、4×4；拖动和缩放后无重叠，重启可恢复布局。
- 拖动一个房间到另一房间时，两者交换位置与卡片尺寸，其他房间布局不变。
- 播放中房间控件默认隐藏，鼠标悬停或键盘聚焦时显示；房间弹幕开关只保留一个；Ctrl+滚轮和边缘拖拽可调整卡片尺寸。
- 移除房间后播放器、弹幕订阅、重连 timer 和音频节点均释放。
- 切换音频焦点只保留选中房间有声；Shift 多选可并行出声；各房间音量相互独立。
- 普通鼠标左键点击房间可立即开启该房间声音并切换音频焦点。
- Shift+左键可独立切换指定房间声音，且不影响其它房间的音频选择。
- 全局弹幕关闭会停止全部订阅，单房间开关只影响对应房间。
- 斗鱼未登录时不能发送；登录后仅能发送合法普通文本，失败时显示真实失败原因。
- 回溯缓存时长约 120 秒且有总内存上限；回放声音正确；导出格式与文件内容一致。
- Windows 重启后能在同一用户下恢复斗鱼登录；更换 Windows 用户不能解密。

### 稳定性与性能

- 4 路、9 路、16 路分别做长时间运行测试；记录 CPU/GPU/内存并检查趋势，不能无限增长。
- 连续添加、移除和切换 50 次后无重复弹幕连接、隐藏播放器或遗留 timer。
- 弱网断开恢复后，各 tile 单独重连，不导致其他房间状态被覆盖。
- 所有房间失败状态相互隔离；单路解析错误不能使工作台整体崩溃。

### 隐私与安全

- 日志、renderer storage、导出 JSON、LAN sync payload 均不包含斗鱼 Cookie。
- localStorage 迁移成功后旧 Cookie 键被清除；迁移失败时用户可恢复，不丢凭据。
- URL 短链解析不能访问本机、私网或非 allowlist 目标。
- 临时导出服务只监听 loopback，令牌一次性、短时有效，应用关闭时停止。

## 8. 主要风险与决策门

| 风险 | 影响 | 应对 / 决策门 |
|---|---|---|
| 16 路硬件解码或网络负载过高 | 播放卡顿、耗电、内存上涨 | 阶段 0 实测；给出推荐配置和性能提示；缓存另设总预算 |
| 音量增强受 CDN CORS 限制 | 增益处理可能无声 | 逐平台/线路验证；不支持时回退普通音量并显示原因 |
| 浏览器录制格式不统一 | GIF/MP4 导出失败或编码差异 | 先验证目标 WebView；必要时评估本地转码器及许可证 |
| 短链可重定向到任意地址 | SSRF 风险 | 后端 allowlist、逐跳检查、禁止私网和限制超时/跳转 |
| 平台弹幕协议变化 | 多路连接或发送失效 | 协议隔离在平台包；单测解析与连接生命周期；显示明确错误 |
| Cookie 迁移时仍暴露在 renderer | 账号凭据泄露 | 后端直接完成扫码存储；迁移后清理旧键；日志和同步脱敏 |
| 大型录制数据经 Wails JSON 传输 | 内存复制、卡顿、崩溃 | 使用流式 loopback 写入或有界分块，避免 Base64 全量 IPC |

## 9. 建议先交付的最小可用版本

推荐先完成阶段 0 和阶段 1，得到稳定的“粘贴链接 → 2×2 多房间播放 → 自由排布 → 本地恢复”闭环；随后实现音频与弹幕。斗鱼发送、DPAPI 和回溯导出分别进入独立阶段，原因是它们涉及协议鉴定、凭据安全和编码/发行体积，不宜与网格基础实现绑在同一批高风险改动中。
